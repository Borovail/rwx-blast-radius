# RWX Blast Radius — план и результаты

## Точка продолжения

**Кандидат для тренировочной отправки — `9794c03269accf8f8497108ac3b0fe97049f0994`.** Чистая сборка из Git-архива этого коммита прошла все 32 модульные проверки, три прогона на 30 официальных примерах и проверку на четырёх независимых изменениях. Результат — 550.255 с и 101.193 с симуляции соответственно, ноль пропущенных коммитов на обоих наборах. Медиана CPU чистой сборки на открытых примерах — 0.829 с, сумма с CPU — 551.084 с.

**Следующий шаг за участником** — создать публичный репозиторий GitHub, запушить ветку по командам в `README.md` и подать URL с указанным SHA на странице RWX. После практического прогона записать серверную оценку и число пропусков в этот журнал. По ним выбрать следующее изменение алгоритма.

**Повторить локально** — `make profile`. На этой машине Docker запускался из временного каталога в WSL Ubuntu. Для возобновления, пока этот каталог существует, выполнить в отдельном терминале `wsl -d Ubuntu -u root -- sh .work/private-docker.sh start`. Запуск из второго терминала — `wsl -d Ubuntu -u root -- make profile 'DOCKER=/tmp/buildathon-docker/docker/docker -H unix:///tmp/buildathon-docker/docker.sock'`. С обычным установленным Docker достаточно первой команды Make.

Воспроизведение из корня — команды в `README.md`. На Windows выполнены прямой запуск Python и официальный `score.py`. Значение 1614.1 с на сайте относится к таблице организаторов. Наш локальный показатель рассчитан на опубликованной выборке и исключает CPU.

Модульные тесты планировщика — `python -m unittest discover -s tests -p test_scheduler.py`. Планировщик использует округление миллисекунд из кода официального скорера. Выигрыш этого шага составляет 105.960 с при прежнем выборе тестов.

Проверка на Linux/amd64 в закреплённом Docker-образе с ограничениями организаторов подтвердила оба результата. Для планировщика три запуска дали одинаковые 1104.510 с симуляции. Медиана CPU процесса составила 0.094 с на локальной машине. Команда повторения — `make profile`.

Модуль `impact.py` проверен отдельно на 22 синтетических сценариях. Среди них изменения внутри функций, фикстуры, ошибки синтаксиса, изменение импорта, строки документации, несовпадение исходника и неполная карта. Команда — `python -m unittest discover -s tests`. На реальном неполном индексе дополнительно проверен возврат к запуску всех тестов.

Профиль обработки Python-патчей показал избыточное копирование всего синтаксического дерева. На тех же 48 деревьях исходной и изменённой версий локальный прогон с cProfile занял 4.35 с до изменения и 0.46 с после. Это измерение отдельной операции, вне конкурса.

При сборе карты на Linux прошли все 1620 пронумерованных тестов и 25 440 подтестов. Один тест, указанный организаторами как пропущенный, был пропущен. В исходной карте около 2.57 млн связей между строкой и тестом, файл занимает 907 111 байт. Медиана CPU селектора в трёх Docker-запусках — 0.750 с. Инструкции для пересборки — в `maps/README.md`.

## Независимая проверка

До расчёта прогнозов выбраны четыре изменения в отдельной копии SQLGlot. Для каждого выполнен весь набор из 1620 тестов. Изменение оптимизатора сломало 10 тестов, правка SQL-фикстуры — один, правка тела теста — один, добавление неиспользуемой функции — ноль. При разметке учитывались ошибки подтестов pytest, даже если итоговый статус родительского теста был PASSED. В контрольном запуске отсутствовал файл `sqlglotc/setup.py`. Три затронутых теста повторно прошли на полном исходном дереве.

На этих четырёх патчах исходная карта дала 124.542 с, карта с уточнением двух тестов — 107.328 с, обе с нулём пропусков. Локальные патчи, эталон, результаты pytest и параметры окружения лежат в `.work/holdout/`. Их использует только оценка. Чтобы повторить, подставить `.work/holdout` вместо `sample` в команды запуска и оценки из README.

После обработки всех 25 тестов результат на независимом наборе составил 101.193 с при нуле пропусков. На 30 официальных примерах локальная медиана CPU Docker-селектора составила 0.746 с, суммарная медиана с CPU — 551.001 с.

Эксперимент с выбором по отдельной строке для некоторых изменений выражений дал ещё 0.008 с экономии в симуляции. Добавочный синтаксический анализ также расходует CPU. Для текущего кандидата оставлен выбор по функции.

Проверена и гипотеза об эквивалентном исполняемом коде при вставке комментария. В базовом SQLGlot есть чтение исходников и обращение к метаданным при импорте. С учётом этих зависимостей эксперимент сохранил прежний выбор. Оба эксперимента остались в локальной исследовательской папке.
